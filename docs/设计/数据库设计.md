# 数据库设计

本文定义设备售后、上门预约、知识发布与排障系统的目标数据合同。24张项目自有表保存业务及支持数据，包含knowledge的索引尝试与事务回查事实；会话与迁移技术表另计。业务机制见[系统设计](系统设计.md)，模块和数据所有权见[项目结构](项目结构.md)，线协议见[接口约定](接口约定.md)。字段、约束和历史保留按业务需要确定，不按表机械生成Controller或CRUD。

## 1. 环境、所有权与通用约束

关系存储采用 MySQL 8.4 LTS / InnoDB；向量独立存放 Qdrant，关键词副本存放 Elasticsearch。开发与业务测试使用 test，生产使用 prod，自动化测试使用独立可销毁实例中的 ci。每个服务、每个环境使用独立数据库、运行账号及迁移账号；可以共用实例，但不能共用业务账号。

| 服务 | MySQL 数据库 | 运行账号 | 结构维护 |
| --- | --- | --- | --- |
| desk-user | desk_user_{env} | desk_user_app_{env} | 所属 Flyway 历史与迁移 |
| desk-ticket | desk_ticket_{env} | desk_ticket_app_{env} | 所属 Flyway 历史与迁移 |
| desk-knowledge | desk_knowledge_{env} | desk_knowledge_app_{env} | 所属 Flyway 历史与迁移 |
| desk-ai | desk_ai_{env} | desk_ai_app_{env} | Alembic 显式迁移 |

{env} 为 test、prod 或 ci；迁移账号按 desk_{service}_migrate_{env} 命名。MySQL 的 schema 与 database 同义，每个环境明确建库，不以同库命名空间代替独立数据库。本文逐表标题中的 desk_user、desk_ticket、desk_knowledge、desk_ai 表示逻辑所有者，实际连接库带环境后缀，业务 SQL 不写死环境库名。运行账号仅获所属库所需的表级权限，审计表限制为读取和插入；无 DDL、跨库、全局管理权限。迁移账号独立执行 DDL，应用不以 root 运行。Qdrant collection 与 ES 知识索引也按环境隔离，由 desk-ai 维护；其他业务服务不直接访问。ES中的业务数据仅为知识关键词副本，运行日志经ELK另存独立数据流，Zipkin采用有界内存存储，均不进入业务ER。

服务内关联用外键，由所属迁移维护。跨服务关联保存稳定 ID，通过可信接口校验，不在同实例上跨服务库联表或建立外键。工单和设备的客户一致性在 ticket 内由复合外键保护，客户组织存在性和角色范围通过 user 核验。

表名用单数英文 lower_snake_case，按业务使用 sys_（身份）、it_（型号与设备）、sd_（工单）、kb_（知识发布）、ai_（解析与排障）。字段同样使用 lower_snake_case。主键统一 id，引用以资源名加 _id 命名，created_by、granted_by 等审计字段表示操作者账号 ID。customer_id 统一表示客户组织，owner_id 表示会话及派生数据的拥有账号。status 表示本表生命周期，publication_status 表示发布态，row_version 用于乐观并发。时刻用 _at 和 datetime(6)，统一保存 UTC；日期用 _on 和 date，服务截止日按 Asia/Shanghai 判断。所有连接 time_zone 固定 +00:00，默认时间使用 CURRENT_TIMESTAMP(6)。Java Instant 与 Python 有时区 datetime 在持久化边界显式转换成 UTC，读取后恢复 UTC 语义，HTTP 仍输出含时区的 ISO8601。datetime(6) 本身不保存时区，不能把本地墙上时间直接写入。毫秒和字节分别用 _ms、_bytes。资源 ID 由所属服务生成，跨服务提交的任务 ID 由发起服务先生成，纯关联表用复合主键。

业务 ID 统一使用 `varchar(32)`，由标准 UUID 去掉四个连字符生成 32 位小写十六进制字符串。Java 使用 `String`，Python 使用 `str`。主键和客户端幂等键使用 `CHECK` 校验 `^[0-9a-f]{32}$`。外键、逻辑引用和复合引用与目标列的类型、长度及格式一致。客户端生成请求或动作幂等键并在重试时复用，唯一范围由各表定义。工单编号沿用独立展示编号。

同一业务ID贯通Java内部HTTP、跨语言Protobuf、MQ信封、JSON快照、ES片段文档键和持久化列。框架会话引用`session_ref`与worker领取令牌`claim_token`使用`varchar(36)`保存规范的小写带连字符UUID，并作格式检查。HTTP/Protobuf的sessionRef均为带连字符UUID字符串。MinerU的任务和文件标识按上游协议保存。原件通过持久化storage_bucket、storage_key和storage_version_id定位OSS对象版本；OSS Version ID是供应商标识，不套用业务ID格式。

结构由各服务所属迁移显式维护，首个DDL使用统一标识及字段合同。标识演进需同步外键、复合键、JSON快照、幂等键、消息与检索键，在隔离库核对历史引用和授权后交付，原件定位不随标识格式任意迁移。

表和字段写中文数据库注释；表使用 utf8mb4 / utf8mb4_0900_bin，保持大小写及尾部空格的精确比较；ID、状态、代码、摘要和对象定位列及其引用列使用一致排序规则。展示文本的模糊检索显式定义比较方式。业务 ID 用 `CHECK (REGEXP_LIKE(id, '^[0-9a-f]{32}$', 'c'))` 限定小写，不因默认不区分大小写而接收大写。SHA-256 为 varchar(64)，同样检查 64 位小写十六进制。

必填字段显式 NOT NULL，必填文本限制非空白，状态由 CHECK 和枚举共同约束。boolean 是 MySQL TINYINT(1) 的别名，增加 IN (0,1) CHECK；整数范围、时间顺序和空值组合均有约束。CHECK 接受 UNKNOWN，涉及可空列必须显式写 IS NULL / IS NOT NULL，不能依赖比较自行拒绝空值。TEXT 最多 65535 字节，接口、模型输出和切片均设字符与 UTF-8 字节预算；大于该界限的实际消费者出现时显式迁移 MEDIUMTEXT，不依赖静默截断。启用严格 SQL 模式，禁止零日期。updated_at 由业务更新显式维护，不使用 ON UPDATE 隐式改变审计；row_version 非负且比较后递增。

快照使用 MySQL JSON，不保存向量列。快照要求 JSON_TYPE 为 OBJECT、schema_version 存在且为正整数；集合放具名字段。ai_chunk.error_codes 单独为 JSON 字符串数组，数据库验证 ARRAY、用例验证每项格式、去重及预算，写入时显式提供 []。JSON 不直接建立普通 B-tree 索引，需要查询的标量由稳定业务列承载；检索数组与部分唯一语义采用本项目明确设计的字段及约束，不照搬其他数据库语法。生成列仅用于当前明确的唯一约束，见各表及第26节并发示例。

约束按 pk_/uk_/fk_/ck_/idx_ 命名，遵守 MySQL 表、列和索引 64 字符上限。CHECK 名称在服务库内唯一，包含表名。外键默认 NO ACTION（InnoDB 立即检查，不支持延迟外键）；复合 FK 指向同顺序、完整的 UNIQUE 列组，不依赖非唯一父键。循环引用按先建表、再 ALTER ADD CONSTRAINT 安装，不用禁用外键检查掩盖迁移次序。已有唯一索引可满足查询时不重复建索引。Pydantic 和 Java 校验与数据库约束分别覆盖各自边界。

三份Flyway历史、Alembic版本及Spring Session JDBC的会话和属性表属于技术数据，不纳入24张自有表。XXL-JOB使用独立xxl_job_{env}技术库、独立账号和同版官方SQL（8张技术表），不套用业务ID和业务表规范；业务服务运行账号不能读写该库，Admin管理触发及执行记录，业务进度仍在所属库。会话表使用框架MySQL方言，由user迁移安装；JDBC Session供身份服务实例共享，账号、角色与授权以user当前事实为准。内部核验使用会话行PRIMARY_ID作为非凭证引用，user核验过期、账号与auth_version；用于Cookie的SESSION_ID仅在user边界内解析。 [Spring Session JDBC表结构](https://docs.spring.io/spring-session/reference/3.5/configuration/jdbc.html)

| 领域 | 自有表数 | 分表依据 |
| --- | --- | --- |
| 身份 | 5 | 组织、账号、角色关系、服务范围、管理审计 |
| 设备、工单与上门 | 7 | 型号、设备、工单、时间线、通知、上门时段、预约 |
| 知识发布 | 5 | 资料系列、资料修订、适用型号、发布事件、索引尝试与事务事实 |
| 排障 | 7 | 索引任务、知识片段、会话、问答运行、引用、报修草稿、反馈 |

工单到时间线、时段到预约、资料系列到修订、索引任务到片段是一对多。资料修订和适用型号是多对多，由关联表表达。一次运行最多有一份反馈，同一草稿最多生成一张正式工单，使用唯一约束。Java索引尝试与AI任务按同一jobId逻辑关联，双方各持本库事实。工单期限沿用工单字段，Redis 限流键、ES/Qdrant检索副本、运行日志不计作关系表。 [MySQL CHECK](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html) · [生成列索引](https://dev.mysql.com/doc/refman/8.4/en/create-table-secondary-indexes.html)

## 2. `desk_user.sys_organization` 客户与服务商组织

| 字段 | 类型 | 空值/默认 | 含义与约束 |
| --- | --- | --- | --- |
| `id` | varchar(32) | 必填，无默认 | 主键，由所属后端生成 |
| `organization_code` | varchar(64) | 必填，无默认 | 规范化小写后全局唯一，停用不复用 |
| `organization_name` | varchar(100) | 必填，无默认 | 展示名称，不作为授权标识 |
| `organization_type` | varchar(32) | 必填，无默认 | CUSTOMER / SERVICE_PROVIDER |
| `service_provider_guard` | tinyint | 可空，STORED 生成 | SERVICE_PROVIDER 为1，否则 NULL；唯一 |
| `status` | varchar(32) | 必填，ACTIVE | ACTIVE / DISABLED |
| `created_at` | datetime(6) | 必填，CURRENT_TIMESTAMP(6) | 记录创建时间 |
| `updated_at` | datetime(6) | 必填，CURRENT_TIMESTAMP(6) | 更新时显式维护，默认值不自动随 UPDATE 改变 |
| `row_version` | bigint | 必填，0 | 非负，更新比较旧值后加一 |

organization_code 唯一且非空白，organization_type/status 使用 CHECK。service_provider_guard 的 UNIQUE 限制 SERVICE_PROVIDER 最多一条，服务商由身份初始化流程建立。

停用组织不删除账号、设备和工单。每次身份核验检查组织状态，客户停用后停止新的客户业务；已有工单仍可由具有当前客户范围的有效服务人员处理。禁止停用唯一服务商导致全部管理员失效，纳入最后管理员保护事务。索引按状态和稳定 ID 支持有界组织选择。

## 3. `desk_user.sys_user` 账号

| 字段 | 类型 | 空值/默认 | 含义与约束 |
| --- | --- | --- | --- |
| `id` | varchar(32) | 必填，无默认 | 主键，由所属后端生成 |
| `organization_id` | varchar(32) | 必填，无默认 | 本库 FK → sys_organization |
| `username` | varchar(64) | 必填，无默认 | 去首尾空格、转小写，全局唯一 |
| `password_hash` | varchar(255) | 必填，无默认 | Spring Security 哈希及算法标识，不能输出 |
| `display_name` | varchar(100) | 必填，无默认 | 姓名，不作授权条件 |
| `status` | varchar(32) | 必填，ACTIVE | ACTIVE / DISABLED |
| `must_change_password` | boolean | 必填，true | 初始化和重置后强制改密 |
| `password_changed_at` | datetime(6) | 可空 | 首次主动改密前为空 |
| `last_login_at` | datetime(6) | 可空 | 仅认证成功更新 |
| `auth_version` | bigint | 必填，0 | 改密、角色、组织、客户范围或停用等认证相关变更加一 |
| `created_by` | varchar(32) | 可空 | 本库 FK → sys_user，首次管理员初始化可空 |
| `created_at` | datetime(6) | 必填，CURRENT_TIMESTAMP(6) | 记录创建时间 |
| `updated_at` | datetime(6) | 必填，CURRENT_TIMESTAMP(6) | 更新时显式维护，默认值不自动随 UPDATE 改变 |
| `row_version` | bigint | 必填，0 | 非负，更新比较旧值后加一 |

username 全局唯一，数据库以 CHECK 限制小写 ASCII 字母、数字、点、下划线及连字符，首字符为字母或数字，长度3至64。auth_version、row_version 非负，停用账号保留用户名。organization_id 和 created_by 为本地外键，账号保留历史。管理列表使用 (organization_id,status,id)。

组织类型与角色组合由 Service 在同一管理事务验证。组织调动只修改当前账号归属，不迁移旧业务记录的客户或拥有者；客户历史读取同时匹配当前组织和原 owner/requester。失去处理权限的技术人员由范围内客服转派，不删除原时间线。改密、重置、停用、角色/组织/服务范围变更增加 auth_version；会话只保存 ID 和版本，在线核验读取当前事实。最后有效管理员保护先锁唯一服务商组织行，再读取并锁定受影响账号和角色，所有组织停用、管理员降权及账号停用入口遵循同一锁顺序。在锁内核对至少一名有效管理员，不只做一次 COUNT 再分别更新。

## 4. `desk_user.sys_user_role` 账号角色

| 字段 | 类型 | 空值/默认 | 含义与约束 |
| --- | --- | --- | --- |
| `user_id` | varchar(32) | 必填，无默认 | 联合 PK，本地 FK → sys_user |
| `role_code` | varchar(32) | 必填，无默认 | 联合 PK，五种固定角色码 |
| `granted_by` | varchar(32) | 可空 | 本地 FK → sys_user，首次初始化可空 |
| `created_at` | datetime(6) | 必填，CURRENT_TIMESTAMP(6) | 记录创建时间 |

联合主键 (user_id, role_code)，按 (role_code, user_id) 支持最后管理员保护和角色查询。role_code CHECK 限定 CUSTOMER_USER、SERVICE_AGENT、TECHNICIAN、KNOWLEDGE_ADMIN、SYSTEM_ADMIN，显示名由应用角色定义提供。角色增删与用户 auth_version 同事务，客户与服务商角色不得混合。

撤销最后一个服务角色时同时清理该用户全部 sys_user_customer_scope；仍保留另一服务角色时范围保留。删除角色关联是显式撤权，不能级联删除账号。

## 5. `desk_user.sys_user_customer_scope` 服务人员客户范围

| 字段 | 类型 | 空值/默认 | 含义与约束 |
| --- | --- | --- | --- |
| `user_id` | varchar(32) | 必填，无默认 | 联合 PK，本地 FK → sys_user |
| `customer_id` | varchar(32) | 必填，无默认 | 联合 PK，本地 FK → CUSTOMER 类型的 sys_organization |
| `granted_by` | varchar(32) | 必填，无默认 | 本地 FK → sys_user，授权管理员 |
| `created_at` | datetime(6) | 必填，CURRENT_TIMESTAMP(6) | 记录创建时间 |

联合主键(user_id, customer_id)，反向索引(customer_id, user_id)。Service 校验用户属于服务商、有 SERVICE_AGENT 或 TECHNICIAN 角色，customer_id 必须为客户组织。范围不是全平台租户管理员权限。

授予、撤销在同事务增加用户 auth_version 并追加管理事件。撤销后按当前权限拒绝访问，客服按当前范围重新指派工单。

## 6. `desk_user.sys_admin_event` 身份管理审计

| 字段 | 类型 | 空值/默认 | 含义与约束 |

| `target_user_id` | varchar(32) | 可空 | 本地 FK → sys_user |
| `target_organization_id` | varchar(32) | 可空 | 本地 FK → sys_organization，与目标账号恰有一个 |

## 7. `desk_ticket.it_product_model` 产品型号

| 字段 | 类型 | 空值/默认 | 含义与约束 |
| --- | --- | --- | --- |
| `id` | varchar(32) | 必填，无默认 | 主键，由所属后端生成 |
| `category` | varchar(32) | 必填，无默认 | COMPUTER / PRINTER |
| `brand` | varchar(100) | 必填，无默认 | 品牌，规范化后参与联合唯一 |
| `model_name` | varchar(100) | 必填，无默认 | 型号，规范化后参与联合唯一 |
| `supported_systems` | varchar(500) | 可空 | 已知系统适用说明，不猜测兼容性 |
| `status` | varchar(32) | 必填，ACTIVE | ACTIVE / DISABLED |
| `created_by` | varchar(32) | 必填，无默认 | 外部逻辑引用 → user 账号 |
| `created_at` | datetime(6) | 必填，CURRENT_TIMESTAMP(6) | 记录创建时间 |
| `updated_at` | datetime(6) | 必填，CURRENT_TIMESTAMP(6) | 更新时显式维护，默认值不自动随 UPDATE 改变 |
| `row_version` | bigint | 必填，0 | 非负，更新比较旧值后加一 |

品牌和型号保留展示大小写，去首尾空格后不能为空。唯一表达式索引按 category 和两个字段的 ASCII 大小写折叠值约束，同一规范化由服务用于输入查重。保持标点、内部空格和后缀，避免把近似型号误合并。型号 ID 稳定，停用保留记录。

客服维护型号；停用拒绝新设备与新文档关联，不使已有设备和文档自动失效。knowledge 仅通过内部型号合同校验，不能增加跨服务库 FK。

## 8. `desk_ticket.it_device` 客户设备实例

| 字段 | 类型 | 空值/默认 | 含义与约束 |
| --- | --- | --- | --- |
| `id` | varchar(32) | 必填，无默认 | 主键，由所属后端生成 |
| `customer_id` | varchar(32) | 必填，无默认 | 外部逻辑引用 → 客户组织 |

storage_key、(created_by,client_upload_id)、(series_id,revision_number) 和 (id,series_id) 唯一，修订号为正。上传前先在当前权限内查询请求回执；同键同摘要返回原修订，同键异义冲突。knowledge先以Redisson按created_by+client_upload_id互斥外部上传，取锁后重查回执；锁在数据库事务外取得且不替代权限核验。并发上传、锁失效或旧请求迟到在提交修订时仍由唯一约束收敛到一个结果，失败事务不占用修订号；未被采用的 OSS 对象进入受控孤立对象对账，不承诺外部存储恰好一次。上传回执未查到只表示尚未看到已提交修订，不能断言 OSS 没有在途写入。Bucket、Object Key 和 Version ID 创建后固定，由知识服务校验允许的环境与长度；不持久化 endpoint、临时签名 URL 或访问凭据。SHA-256 来自真实文件字节，OSS ETag 不作为 SHA-256，也不假定所有上传方式的 ETag 都等于 MD5。系列内 PUBLISHED 与 DISABLED 合计最多一行，由 current_series_id UNIQUE 保证。DELETED 与 deleted_at 对应。published_at、published_by 同空同有，PUBLISHED、DISABLED、RETIRED 必须有已发布标记、当前任务及来源复核记录。索引提交/取消事务状态来自Java业务任务，受理及执行状态经AI RPC查询，不伪造统一发送态。

current_job_id仅允许DRAFT在前次submit_state=ABORTED，或前次提交已COMMITTED且AI终态/解析收敛后切换；前次SUBMIT/CANCEL仍PREPARING或AI结果未知不切换，首次准备同样锁文档登记；已发布修订不新建索引尝试、不取消其成功任务，也不修改已有片段。新的解析/切片/向量空间通过新 DRAFT 修订重新验证与发布，同空间副本重建沿用旧片段身份。

发布和恢复先核对 AI 成功任务和片段，再锁系列、修订与当前Java任务，比较row_version/current_job_id，submit_state须COMMITTED、cancel_state为NONE或ABORTED，AI lastCommand须SUBMIT。替换时先退役旧修订，再发布同系列的较新修订，并追加两条相关事件，整个动作一次提交。replaces_document_id 非空唯一，禁止自指。前驱须为切换前的 PUBLISHED 或 DISABLED 版本且修订号较低。已发布资料的原件和适用范围固定，变更通过新修订。型号范围变化需要管理员确认差异并在事件留痕。

停用保留该系列的当前修订位置。恢复只作用于当前 DISABLED 修订。删除仅用于从未发布的DRAFT；从未建索引可直接按版本删除，有索引尝试则须各尝试submit_state=ABORTED，或取消已COMMITTED且AI lastCommand=CANCEL、任务终态/解析收敛；保留业务事务事实及取消墓碑，不能以AI NOT_FOUND证明无在途消息。并须确认无活跃索引、无SUBMITTING/ACTIVE/UNKNOWN远端解析；有未收敛任务时先取消和对账，已发布资料通过停用或替换退出检索，指定 OSS 对象版本与历史引用保留。管理列表按系列和修订号查询，检索授权从型号反查后筛选 PUBLISHED。失败草稿或孤立对象回收先核查记录、任务、引用和在途提交；版本控制不代替备份，生命周期规则不得提前删除被引用版本。不建立自动物理删除任务；孤立对象物理回收在暂停上传并核对在途提交收敛的运维窗口执行，不仅凭对象年龄判断。

(document_id,attempt_number)、(id,document_id)、(requested_by,client_request_id)唯一。业务任务是管理回执、尝试身份和事务事实，不是outbox；没有delivery_status、自动重发次数、next_attempt_at或发送领取字段，不建立定时发送器。client_request保存原document_id、row_version及处理配置，同请求键先比原输入再返回原状态；command_input保存已分配jobId的不可变输入，与MQ的requestHash核对。信封输入对同jobId固定，SUBMIT operationId=id，CANCEL operationId=cancel_operation_id；浏览器只能提供幂等键，不能指定服务器jobId。

准备登记短事务锁文档→本地任务，核对DRAFT及前次收敛，保存PREPARING、UTC截止及current_job_id并递增文档row_version，确认阶段沿用准备提交后的版本。准备不等于业务已接受，重复同请求只返回原进展，不重复发送。半消息在事务外发送；明确取得半消息回执后，确认事务重新按文档→任务锁定并另取MySQL UTC时刻，仅在当前版本/任务匹配、PREPARING且决策时刻未过截止时提交COMMITTED和对应资料事件。数据库锁不跨网络，MySQL COMMITTED后才向Broker COMMIT；二次确认失败不能反向改ABORTED。

CHECK限定submit_state的有效字段组合，PREPARING→COMMITTED/ABORTED单向迁移由条件更新保证；submit_deadline_at>created_at，提交时间不早于created_at。允许确认事务在截止前取得决策锁、截止后才完成提交，其他回查/收敛操作必须等待同一行锁，不能仅按墙钟推翻已开始的确认。SQL事务总预算5秒、锁等待有界，knowledge连接另设服务端空闲上限及失效检查，参数见部署说明；应用暂停时不能无限持有决策锁或在Broker回查耗尽后迟到提交。准备过期的收敛事务以同一文档→任务锁序更新PREPARING→ABORTED，提交后回查才能ROLLBACK，恢复的旧请求不再有提交资格。

cancel_state=NONE时cancel_operation_id/cancel_requested_by/cancel_deadline_at/cancel_committed_at全空；非NONE要求前三者非空，且submit_state=COMMITTED；cancel_committed_at当且仅当取消COMMITTED非空。首次取消NONE→PREPARING，随后COMMITTED或ABORTED；仅ABORTED可读取最新文档版本后显式再准备并替换cancel_operation_id，已COMMITTED不回退或覆盖。取消PREPARING禁止发布/切换尝试，确认事务同样重核DRAFT、当前任务、准备后的版本及截止，并原子写取消提交时刻和INDEX_CANCEL_REQUESTED事件。所有SUBMIT/CANCEL准备、确认及终止均在同一事务递增文档row_version；既有提交/准备先返回原回执，新操作再校验版本，阻止旧取消请求自动开启新操作。对旧取消operationId回查，若与当前不符则证明旧操作未提交，可ROLLBACK；已提交取消不替换ID。

TransactionChecker匹配jobId、输入摘要及operationId；已COMMITTED→COMMIT，已ABORTED→ROLLBACK，PREPARING未到期/数据库失败/锁等待→UNKNOWN。查不到预登记业务记录属异常，不能因一次未见就猜ROLLBACK。历史SUBMIT提交证明不会因当前任务已取消、已换版或终态而失效；重放已提交原指令只依赖已有提交事实，不重复业务变更。业务证明保留到所有可能回查/重放和历史引用结束，默认不物理删除。半消息超预算或Broker数据丢失不由本表自动投递，管理员核对后沿原身份受控重放。

索引提交202只在本地COMMITTED后返回。半消息失败/未知且本地未提交时返回失败/未知，原键查询PREPARING/ABORTED；同键ABORTED不复活，新业务尝试才分配新clientRequestId/jobId。AI受理/执行事实不复制进本表；GetStatus核对摘要/lastCommand。仅本地SUBMIT提交、无准备中/已提交取消、AI成功及远端收敛才能发布。以(submit_state,submit_deadline_at,id)、(cancel_state,cancel_deadline_at,id)索引有界收敛过期准备；没有AI任务的ABORTED尝试也可安全结束，不凭不存在的远端任务等待。

| `updated_at` | datetime(6) | 必填，CURRENT_TIMESTAMP(6) | 更新时显式维护，默认值不自动随 UPDATE 改变 |

任务ID与Java索引尝试kb_index_job.id一致。(id,document_id)唯一供片段复合FK，(document_id,attempt_number)唯一，active_document_id UNIQUE限制每文档至多一个QUEUED/RUNNING。以(status,created_at,id)领取任务，(status,claim_until,id)恢复过期执行权。MQ相同jobId同request_hash幂等受理，不同输入记协议冲突并进入有界重投/死信，不ACK为成功。取消先到用完整输入写CANCELLED墓碑和last_command=CANCEL，晚到SUBMIT只保留原结果。活跃任务取消原子清空执行权并写终态；已终态保留原状态同时记录last_command=CANCEL，重复不重置阶段或started_at。受理事务提交后才ACK；AI进程仅通过IndexJobService/GetStatus提供内部任务查询。CANCELLED要求last_command=CANCEL；last_command=CANCEL不要求执行终态一定是CANCELLED，因为成功/失败可能先提交。

MinerU 和 Embedding 在事务外。调用 MinerU 创建前持久化 SUBMITTING，收到已知远端 ID 后持久化 ACTIVE，确认远端已终止后记 SETTLED。创建结果未知且无 ID 时记 UNKNOWN。仅 NOT_SUBMITTED 或 SETTLED 表示远端已收敛。没有远端 ID 时，受控运维命令需确认旧解析执行环境已隔离且任务不会恢复，才能在同一事务写入 parser_reconciliation 并改为 SETTLED。SUCCEEDED 要求 started_at、有效页数、SETTLED 及 ES/Qdrant 两路索引均通过验证。在有界本地事务内一次固定完整切片清单及稳定 ID，并由 CHUNKING 进入 EMBEDDING；不能把部分已存片段当作完整解析。超出页数、片段数或事务预算时明确失败。索引外部写入前持久化 INDEXING 阶段。向量在事务外由百炼生成并写入 Qdrant，关键词写入 ES；按 job_id 核对两路完整 ID 集合、数量、载荷和查询可见性后，才条件提交 SUCCEEDED。任一路失败都不得发布；重启先检查已有条目，只补缺失或不匹配的批次，同 ID upsert，不重新解析。Qdrant 已有向量可复用；尚未持久化的 Embedding 结果可能需再次付费生成，不能承诺跨库恰好一次。取消或迟到索引回执不能将任务置为成功，迟到副本因无成功授权任务不可被召回。RUNNING 要求 started_at 与 stage，finished_at 当且仅当终态有值，FAILED 要求 error_code。取消后的迟到回执可用于清理远端任务，不能写片段或改变本地终态。发布状态由 knowledge 决定。

RUNNING 当且仅当 claim_token、claim_until 非空；QUEUED 与终态清空执行权。worker 在短事务中从 QUEUED 领取，或者比较过期租约接管 RUNNING；续约、阶段、片段和成功提交均须匹配当前令牌及有效租约。取消与失败终态同步清空执行权，旧 worker 不能覆盖新领取者或终态。恢复时，PARSING 沿原 MinerU 标识查询；SUBMITTING 且无远端 ID 按 UNKNOWN 对账，不重新创建；切片清单已固定时只补齐已有 ID 对应的外部副本。已取消任务的远端回收按 parser_state 和原任务身份单独对账，不能复活本地任务。租约不代表远端进程已停止。

使用 (index_job_id,chunk_number) 唯一索引和 (document_id,index_job_id) B-tree。MySQL 保存正文、来源、任务和历史引用事实，不再保存 embedding 列。ES 的文档 ID 为片段 ID，保存受控关键词副本；Qdrant 的 point ID 由同一 32 位 ID 无损转换成带连字符 UUID，payload 保留原始 chunk_id、index_job_id、document_id 和 vector_space。原始 ID 与 point ID 一一对应，不随机生成第二个片段身份。

Qdrant 初始 collection 为 desk_chunks_{env}_te4_1024_v1，向量配置 size=1024、distance=Cosine，向量模型及预处理空间版本固定在任务 processing_config。为 index_job_id、document_id、vector_space 创建 keyword payload 索引。通过 HTTPX 调用 REST，批量 upsert 使用 wait=true，并核对已完成响应及实际查询可见性；超时按原 ID 对账后重送。查询使用 /collections/{collection}/points/query，filter.must 限定授权 index_job_id 集合与 vector_space，params.exact=true，固定使用精确召回。Qdrant 不负责调用模型。

知识服务返回的当前修订及任务是授权依据；payload 不能成为权限事实。两路均在查询前过滤，融合后按 ID 批量回查 MySQL 核对任务、文档及正文，交付前重新核验知识发布版本。空授权不发无过滤查询。ES 可直接按 MySQL 片段重建；Qdrant 优先使用完整 snapshot 恢复。没有可用向量快照时，需要按原模型空间重新调用 Embedding、校验费用预算与效果；供应商模型不可用或空间改变时走新任务和知识版本复核，不能假定从 MySQL 零成本恢复原向量。更换模型、维度或预处理必须建立新 collection，并在受控重建和知识任务切换完成后统一更新查询配置；不混用新旧空间。

## 26. 并发、恢复与存储边界

trace_context可空；非空时为带schema_version=1的JSON对象，仅允许traceparent和可选tracestate，序列化上限2KiB，分别按W3C格式及长度校验。无baggage、凭据和业务正文，不参与request_hash或权限判断；非法传输上下文丢弃后保存新建合法上下文，不拒绝合法业务。kb_index_job保存初始提交上下文，AI索引/问答保存首次受理上下文，供重启后的worker接续；采样和Zipkin丢失不影响执行事实。

同一服务中的完整动作由本地事务承担，外部模型、MinerU 和服务请求在事务外执行。跨服务校验与短事务之间仍存在时间窗口，提交时核对本地版本与外部身份快照，后续读取再核对当前授权。

工单动作、处理记录及相关通知原子提交。预约结果、容量、事件及通知在同一请求事务提交，不设置预约outbox。索引由MQ接收进程短事务持久受理后ACK，独立worker再执行长任务；本地指令提交、AI受理及执行成功独立。先锁设备再锁工单的入口仅用于取得设备资料或校验登记，已有预约的操作统一使用工单 → 预约 → 时段。发布、关停只锁时段。knowledge索引准备/提交/取消事务事实在本库持久化，索引运行及远端收敛在 AI 库持久化。AI 排障运行登记与结果使用本地条件事务。结果未知沿原身份核对，期限扫描与用户动作使用同一工单并发条件。

XXL-JOB触发ticket期限及knowledge过期索引准备收敛，处理器调用本服务Service；同批不再注册@Scheduled。多实例及重复触发使用本库领取/条件更新，停机漏扫按状态和期限收敛。Redisson仅对同一上传请求串行外部OSS写入，不替代SQL幂等或索引执行权；锁丢失后唯一回执及孤立对象对账仍有效。XXL技术库只保存调度配置与执行记录，Python长任务由自身worker执行。

AI持久队列领取使用显式短事务中的SELECT ... FOR UPDATE SKIP LOCKED，按到期时间和ID有界选取，再按ID/状态条件UPDATE设置claim_token与claim_until，提交后才访问HTTP、gRPC或模型。执行回执按令牌和状态CAS；MySQL不使用UPDATE ... RETURNING，也不将领取锁持有到外部调用结束。业务连接采用READ COMMITTED隔离级别，锁定读与条件更新承担并发正确性；保持工单→预约→时段的顺序，死锁及锁等待超时只在无外部副作用的完整短事务内有限重试，沿用原幂等键。knowledge准备收敛先无锁选取有界候选ID，再按文档→任务锁序重核并更新，不先锁任务造成反向锁序。

MySQL 不支持部分唯一索引。下列可空 STORED 生成列由数据库计算，业务写入、DTO 和 JSON 快照不赋值；非活动记录返回 NULL，普通 UNIQUE 允许多条 NULL。状态转换时仍锁对应组织、工单、资料系列或会话根行，唯一约束是并发兜底，不替代业务检查。示例不硬编码环境库名，实际 DDL 由所属迁移安装：

```sql
ALTER TABLE sys_organization
    ADD COLUMN service_provider_guard TINYINT
        GENERATED ALWAYS AS (CASE WHEN organization_type = 'SERVICE_PROVIDER' THEN 1 ELSE NULL END) STORED,
    ADD UNIQUE KEY uk_sys_organization_provider (service_provider_guard);
ALTER TABLE ai_generation
    ADD COLUMN active_conversation_id VARCHAR(32) COLLATE utf8mb4_0900_bin
        GENERATED ALWAYS AS (CASE WHEN status IN ('QUEUED', 'RUNNING') THEN conversation_id ELSE NULL END) STORED,

    ADD COLUMN active_document_id VARCHAR(32) COLLATE utf8mb4_0900_bin
        GENERATED ALWAYS AS (CASE WHEN status IN ('QUEUED', 'RUNNING') THEN document_id ELSE NULL END) STORED,
    ADD UNIQUE KEY uk_ai_index_job_active (active_document_id);
ALTER TABLE sd_onsite_booking
    ADD COLUMN active_ticket_id VARCHAR(32) COLLATE utf8mb4_0900_bin
        GENERATED ALWAYS AS (CASE WHEN status = 'CONFIRMED' THEN ticket_id ELSE NULL END) STORED,
    ADD UNIQUE KEY uk_sd_onsite_booking_active (active_ticket_id);

    ADD COLUMN current_series_id VARCHAR(32) COLLATE utf8mb4_0900_bin
```

最后三个约束直接使用原有可空列，无需额外生成列。人工动作的 actor_id、client_action_id 必须同时有效，CHECK 禁止用 NULL 绕过人工动作幂等；系统及无预约事件的对应空值允许重复。所有扫描改为有前导等值状态列的普通复合索引，在真实数据规模用 EXPLAIN ANALYZE 验证，不把 PostgreSQL WHERE 索引语法带入迁移。

文档与实际上下文分别保留标识，已发布 OSS 对象版本、实际使用的片段和历史事件不随停用或退役物理删除。草稿过期保留已建工单，账号禁用保留历史。保留期限和物理清理按实际要求制定。备份窗口暂停知识上传、索引写入、发布与清理并等待在途写入收敛，再按部署说明联合备份四个MySQL服务库、XXL技术库、Broker数据/消费配置、Nacos/Sentinel规则、Qdrant collection snapshot、模型空间及被引用OSS版本/原件。恢复到独立环境校验 snapshot、向量数量/ID/空间、文件摘要、关系、授权与历史引用，再重建 ES；不能把 MySQL 事务当作跨 MySQL/Qdrant/ES/OSS 的一致快照。跨 Bucket 恢复产生的新 Version ID 经受控映射同步数据库。

MySQL DDL通常隐式提交，Flyway/Alembic迁移不能依赖整份脚本回滚。迁移前备份、逐项验证，失败先核对已生效结构，修复后再按明确步骤恢复迁移历史，不默认clean/baseline或盲目重跑。用真实MySQL8.4验证格式CHECK、JSON、生成列唯一、复合FK、UTC、锁竞争及并发预约容量和重复取消回补；H2/SQLite和旧PostgreSQL样例不构成通过证据。Qdrant验证1024维、过滤、幂等写入、断电重启及snapshot恢复；两路失败、准备到期与迟到提交、本地提交后二次确认丢失/回查、取消乱序、落库后ACK丢失、回查/消息预算外受控重放、删除时在途消息及发布闸门必须真实联调。
