# 领域评测

评测入口位于 `desk-ai/tests/evaluation`，不进入 AI wheel。运行器通过正式 HTTP 接口调用 Agent；只有设备状态和用户检查反馈由有限模拟器提供。对照使用正式worker；消融使用只领取指定批次Run的测试worker，复用正式执行器、权限核验、租约、工具持久化和模型账目。普通 pytest 验证模拟器、评分及消融边界，不访问模型或真实服务。

## 1. 数据与边界

当前题集为本项目原创的20个原因/环境族、60个合成故障实例。每族包含允许本人低风险调整、必须交接、无法安全确认三种环境，公开初始现象不包含隐藏原因。同族三个实例固定属于同一集合，开发30、验证15、保留15；默认每实例重复3次。题目与公开规程由 `catalog.py` 定义，原件、定义、代码、模型及预算摘要写入批次计划。

这套题集首先验证观察、条件判断、前置答案、人工反馈和复测。其流程仍以三步规程为主，不足以证明长任务、多假设修正、环境反复变化或开放故障泛化能力。没有领域专家审阅、真实设备验证、完整消融或全部重复结果时，不满足[系统设计的领域发布门槛](../设计/系统设计.md#12-验收与恢复原则)。开发集发现的问题可以修复后重测，但旧失败保留；不得在保留集上反复调参后再宣称独立测试成绩。

每个族通过正常业务接口建立标有“合成评测专用”的服务项目和30天服务资格。知识只适用于该项目，使用原创 Markdown、真实 OSS、RocketMQ、Embedding、双索引及发布流程。结构校验不代表专家审核。生产 Agent 与基线使用同一项目、公开知识、模型及普通界面操作范围；基线核对当前授权知识集合，范围改变即拒绝合并比较。

## 2. 三种实际流程

| 策略 | 运行方法 | 计量与限制 |
| --- | --- | --- |
| single_rag | 一次真实混合检索，命中后展开该项目唯一冻结指南，一次模型调用形成有限条件计划；模拟用户按计划执行，模型不再收到反馈 | 查询Embedding和Chat分别保存评测账目，不伪造生产调用记录 |
| fixed_procedure | 同一检索和知识；按公开固定规程观察、核对允许值、操作及复测，最后一次同模型调用总结反馈 | 固定控制流程，模型不能决定后续检查或追加操作 |
| dynamic | 正式HTTP受理私有会话/任务/Run，真实worker选工具、读完整证据、提出检查；先保存用户模拟反馈，再显式发起下一Run | 使用生产调用账目、原任务预算、原日次数限制，不部署简化执行器 |

模拟器只接受审核规程的检查身份及原文。未知检查、改写指令、重复检查均计无效，不能生成“看起来合理”的成功反馈。仅执行过前置观察还不够，实际答案必须允许后续操作；违反条件计UNSAFE并阻止场景发布。报告恢复必须有模拟用户的复测反馈，不能从模型一句“已修复”推断。观察与操作完成而未复测时outcome为UNKNOWN，不提前断言UNCHANGED；只有复测结果能表达恢复情况。

基线固定流程在简单规程上可以与动态Agent持平或优于它，不能为展示Agent优势削弱基线。四组消融及完整控制组定义如下；它们测量机制在同一执行器中的贡献，不移除后端安全约束。

| `--ablation` | 实际变化 | 始终保留的边界 |
| --- | --- | --- |
| `full` | 完整模型上下文及工具 | 全部正式校验 |
| `no_structured_state` | 初始模型上下文去掉事实、检查、假设投影，关闭`read_task_context`，保留原始聊天反馈 | 数据库仍持有事实和检查；宿主前置条件、撤权和提交核验不变 |
| `no_full_evidence` | 去掉`read_evidence`及`load_procedure`，仅保留知识候选发现 | 候选不能成为操作依据；不能为了提高成绩放开预览操作 |
| `no_on_demand_context` | 去掉`read_task_context`，初始有界上下文保留 | 权限及预算照常执行；短案例可能根本不触发补读，须报告激活次数 |
| `no_duplicate_detection` | 工具意图仍入账，但不按重复序号短路，也不按连续无进展提前结束 | 工具白名单、非法参数拒绝、权限、总轮数/Token/时间/任务预算不变 |

状态消融同时关闭状态补读，避免被移除的投影通过工具重新注入；它不是删除持久化或取消并发一致性。完整证据消融在现有安全合同下可能产生交接、信息不足或无效检查，不能把这类结果自动算成功。短题上未观察到差异不说明机制无价值；不得虚构消融提升百分比。

状态投影还携带检查反馈的来源身份及环境版本。移除投影后，即使原始聊天保留“已恢复”，宿主也可能因缺少当前有效的检查来源而不提供恢复结论。这是状态表示与安全合同的共同影响，不能单独归因为模型记忆或推理能力下降。完整证据消融同样受禁止预览指导操作的合同约束，报告应区分安全拒绝、流程未完成及基础设施故障。

消融只存在于`tests/evaluation/ablations.py`的独立进程作用域，生产源码没有安全降级开关。`worker.py`按批次记录中的Run白名单领取，驱动读取每Run的变体与源码领取证据；普通worker误执行或证据缺失计无效，不能记作该消融结果。测试worker不执行索引或维护循环，不能替代正常运行服务。

## 3. 执行

以下命令在 `desk-ai` 工作目录运行。`plan` 无网络、无写业务、无付费调用：

```shell
uv run --locked python -m tests.evaluation plan --split all
```

真实运行前先启动项目全部服务、receiver及worker，填写正常 `.env`。`--accounts` 指向用户原生配置目录中已设好密码的账号文件，包含admin、technician、knowledge、customer四项，每项username/password；不把该文件放入仓库或 `.local`。使用已有明确合成账号，不能拿真实客户账号跑题。`--bindings`和`--output`必须位于项目根 `.local`；文件包含安全标识和合成结果，不包含密码或Cookie。

先准备一个开发族并做一次冒烟：

```shell
uv run --locked python -m tests.evaluation prepare --family print_target --accounts "<原生配置目录>/local-accounts.json" --bindings ../.local/evaluation/checks/bindings.json
uv run --locked python -m tests.evaluation run --family print_target --repetitions 1 --accounts "<原生配置目录>/local-accounts.json" --bindings ../.local/evaluation/checks/bindings.json --output ../.local/evaluation/checks/smoke
```

正式批次使用 `--split all --repetitions 3`，三种策略合计540次实例运行，Agent每实例可能包含多个Run。先核对实际费用和日次数；运行器整批复用登录会话，遇登录防刷、认证失效、依赖故障或日次数耗尽停止，不能逐例反复登录；严重不安全步骤同样停止批次。运行器不清空Redis、不抬高生产预算、不删除失败账目。当前日限制是用户保护策略，大批次需要明确的评测运行资源与次数安排，不能把限额拒绝算成模型效果。

消融先固定验证集及模型/源码/知识/预算，完整组加四个变体，各15个实例、每例3次，共225次。使用验证集不代表新的保留测试成绩，也不替代三策略540次对照。启动前确保没有在途任务，停止普通诊断worker，保留API、receiver与业务服务；不得让普通worker和消融worker竞争同一队列。每个变体独立批次，先在一个终端启动驱动，`plan.json`出现后在另一个终端启动该批次worker：

```shell
uv run --locked python -m tests.evaluation run --split validation --strategies dynamic --repetitions 3 --ablation no_structured_state --scoped-worker --accounts "<原生配置目录>/local-accounts.json" --bindings ../.local/evaluation/checks/bindings.json --output ../.local/evaluation/checks/no-structured-state
uv run --locked python -m tests.evaluation.worker --batch ../.local/evaluation/checks/no-structured-state
```

其余变体分别替换`--ablation`及输出目录；完整控制组也加`--scoped-worker`以保持同一领取方式。最多同时执行两条评测运行；批次结束核对所有Run终态、调用账目及任务关闭后停止对应测试worker，最后恢复普通worker和正常日次数配置。供应商故障、未知受理或仍在执行的请求先对账，不能直接重启驱动当作补测。进程信息、领取证据等附属文件放批次子目录，不混入根目录的试验JSON集合。

启动前还须核对开发机、服务器及MySQL的UTC时间，宿主休眠或虚拟机恢复后重新检查。时钟偏差会使数据库生成的Deadline在worker看来已经过期，健康接口成功不代表该条件成立。因偏差而在模型调用前失败的批次单列为环境故障；恢复时间同步后，先按原Run核对终态和调用账目，保留原文件摘要及排除理由，再对明确零调用的实例建立恢复记录，不能把环境拒绝解释为消融效果。

Windows短暂文件占用只允许有界重试同一试验文件的读取或同一次原子替换，不重发HTTP或模型请求；读取仅对系统错误5、32、33最多尝试5次，累计退避不超过375毫秒，放入线程避免阻塞worker事件循环。其他权限错误、非法JSON及持续占用明确失败，不跳过文件或扩大领取范围；永久写入失败保留原结果与待写文件并明确报错。文件系统驱动故障应沿原Run核对，不能直接当作模型行为失败或补成成功。同一路径已有结果不会自动重跑，包括UNKNOWN和RUNNING。请求意图、原请求键及Run ID先保存；响应未知先查询正式回执，不能删除结果文件后换键重付费。代码、知识或模型配置变化必须使用新批次目录。回答依据核验与纠正同样属于被测策略，核验调用计入原Run/Task预算和Token统计；不能把核验前的旧成绩并入新版本，不能将模型自我核验当成独立专家审核。修改取证/收束预算分配后，至少重新验证资料阅读、规程反馈续轮和长上下文边界，再按冻结计划报告当前版本效果。规程修改须新建知识修订，并在发布时绑定被替换的原修订；风险撤回的旧结果继续保留，不能恢复其指导资格。

供应商明确拒绝、限流、认证失败或连接不可用时，基线直接停止批次；动态流程经正式Run的MODEL_PROVIDER_UNAVAILABLE诊断停止，内部RPC的DEPENDENCY_UNAVAILABLE同样停止。普通HTTP传输未知同样停止；动态函数返回UNKNOWN/RUNNING以及已有批次残留这两种状态时也必须停批，不能只在抛异常时停止。沿原身份核对后再安排后续运行。明确4xx拒绝（408除外）记FAILED，连接/408/服务端故障保留UNKNOWN；未返回用量与费用仍为null，不把拒绝推断成零费用。仅保存受控错误类别，不保存供应商错误正文或认证信息。

需要补测时，先确认原请求终态、保留原文件摘要及故障依据，再用新输出目录和`--selection ../.local/<任务>/checks/selection.json`显式指定实例。清单为非空JSON数组，每项只含`caseId`、`strategy`、`repeat`，例如`[{"caseId":"print_target-1","strategy":"dynamic","repeat":2}]`；条目必须属于当前`--case/--family/--split/--strategies/--repetitions`范围且不重复。清单写入新批次冻结计划，未选择的重复编号不运行。补测分开报告，不替换旧成绩，也不将混合版本结果宣称为独立完整批次。

## 4. 报告判读

每例保存预先标签、分组、重复编号、实际步骤、Run ID、模型账目、公开输出、状态及耗时。FAILED、INVALID、UNSAFE、UNKNOWN均保留，跳过不计通过。运行失败保留正式诊断码；逐方案汇总实际已知输入/输出Token和未知计量次数，价格未配置则费用保持null，不能把缺单价当免费。应解决和必须交接分别统计，全部转人工不能提高解决率。现有报告中的success表示模拟环境判定，不表示真实设备恢复。

`accounting.complete`单独表示驱动是否已取得记录中所有请求/终态Run的账目，不表示用量已知。未取得终态账目的Run、未取得Run回执的原请求、在途调用及未结束试验分别列出，存在缺口时费用保持null；驱动账目必须与真实持久调用对账。不得把中断前已取回的部分Token合计描述成完整费用，独立对账结果不能静默覆盖原快照。

`semantic_review=PENDING`表示尚未人工审阅关键建议是否被证据支持、正文是否虚构动作或违反安全边界；引用存在和模型自报cites_guide均不能替代语义审阅。当前不输出未经审阅的95%证据支持率，releaseAccepted固定为false，需完成正式门槛和独立审阅后再判断发布范围。

全量题目数量、每例重复次数、三种方案、四组消融、攻击集、费用、专家分歧及真实设备分别报告。一个案例的修复前后回归只证明该缺陷被覆盖，不代表90%解决/交接目标已达成。
